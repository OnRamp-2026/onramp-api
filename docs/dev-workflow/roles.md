# 역할 — Claude Code 단독 운영 (메인 세션 vs 서브에이전트)

> 이 레포는 **Claude Code 하나로** 워크플로우를 돌린다. Codex는 쓰지 않는다.
> 대신 "실행"과 "검토"를 **컨텍스트로 분리**한다 — 같은 도구라도 세션이 다르면 맹점이 줄어든다.

## 메인 세션 = 실행자
- 코드베이스 **리서치**, **계획서** 작성, 승인된 계획 **구현**.
- 테스트 작성·실행, 타입체크, lint, **검증 루프** 주도.
- 리팩터·인수인계 문서·커밋.
- 스킬: `/research-plan` · `/implement-from-plan` · `/test-plan` · `/tdd` · `/refactor-clean` · `/handoff`
- 커맨드: `/verify` · `/commit` · `/pr` · `/context-check`

## 서브에이전트 = 검토자 (격리 컨텍스트)
`.claude/agents/` — 메인 세션의 대화 맥락을 물려받지 않고 **코드만 보고 판단**한다. 그래서 "내가 방금 짰으니 맞겠지"가 끼어들지 않는다.

| 에이전트 | 언제 | 역할 |
|---|---|---|
| `planner` | 계획 단계에서 설계 대안이 필요할 때 | 리서치 → 계획서 초안. **구현 안 함** |
| `code-reviewer` | 구현 후, 커밋 전 | 변경 리뷰 → 심각도별 보고. **자동 수정 안 함** |
| `tdd-guide` | 테스트 계약을 먼저 세울 때 | 실패 테스트 작성·검증 |

호출: `code-reviewer 서브에이전트로 이 변경 리뷰해줘` 처럼 이름을 지정한다.

## 규모가 커지면 — 구현자도 분리한다 (`/subagent-driven-development`)

위 방식은 **구현은 메인 세션, 리뷰만 분리**다. 계획서의 태스크가 4개 이상이고 서로 대체로 독립적이면 **구현자까지 태스크별로 분리**한다.

```
태스크 N: 신규 구현 서브에이전트 → 구현·테스트·커밋·자기점검
          ↓ (리뷰 패키지 = diff 파일)
       별도 리뷰 서브에이전트 → 스펙 준수 + 코드 품질 판정
          ↓ 지적 있으면 fix 라운드 (최대 5회, 4회차부터 상위 모델)
       ledger에 기록 → 다음 태스크
          ↓ (전체 태스크 완료 후)
       whole-branch 최종 리뷰 (최상위 모델)
```

**왜 더 강한가:**
- 구현자와 리뷰어가 **다른 에이전트**다. 자기 코드를 자기가 승인하는 구조가 성립하지 않는다.
- 구현자는 **태스크 브리프 파일만** 받는다. 이전 태스크의 대화·정당화를 물려받지 않으므로 "아까 그렇게 하기로 했으니까"가 없다.
- 지적을 컨트롤러(메인 세션)가 직접 고치지 않는다 — 고치면 리뷰를 건너뛴 코드가 된다. **구현자에게 되돌린다.**
- fix 라운드 상한(5회)이 있고, 초과하면 **사람에게 보고**한다. 무한 수정 루프를 구조적으로 막는다.
- 진행 상황을 `ledger` 파일에 남긴다 — 컨텍스트가 압축돼도 이미 끝난 태스크를 다시 돌리지 않는다.

**주의:** 서브에이전트를 여러 개 쓰므로 토큰 비용이 는다. dispatch할 때 **모델을 반드시 명시**한다(생략 시 세션 모델 상속 = 최고가). 기계적 태스크는 `haiku`, 통합/판단은 `sonnet`, 최종 리뷰는 `opus`.

## 빌트인 리뷰 명령도 같이 쓴다
- `/code-review` — Claude Code 빌트인. 현재 작업 diff를 리뷰. **이게 1차 리뷰다.**
- `/security-review` — 브랜치 변경의 보안 리뷰.
- `/review-checklist` — 이 레포의 팀 체크리스트(`verification-loop.md`)로 점검. 빌트인이 놓치는 **프로젝트 고유 항목**(RAG 지표·의존성 고정·계획 이탈)을 잡는 용도.

## 왜 이렇게 나누나
- **자기 코드 자기 검토의 맹점**은 도구를 바꿔서가 아니라 **컨텍스트를 끊어서** 줄인다. 구현 대화를 다 본 세션은 자기 판단을 재확인하는 쪽으로 기운다.
- 검토자는 **보고만** 하고 고치지 않는다. 고칠지는 사람이 정한다.

## 경계
- 서브에이전트는 코드를 직접 수정하지 않는다(`tdd-guide`의 테스트 작성 제외).
- push/PR·배포는 **어느 쪽도 자동으로 하지 않는다** → 사람 승인.
- 최종 판단자는 사람이다. 리뷰 결과가 갈리면 사람이 결정한다.
