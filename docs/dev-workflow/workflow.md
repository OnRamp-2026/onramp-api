# 개발 워크플로우 — Research → Plan → Approve → Implement → Test → Review → Handoff

> AI에게 바로 구현을 맡기지 않는다. 각 단계는 **AI가 할 일 / 사람이 확인할 것 / 산출물**이 나뉜다.

## 전체 흐름
```
요구사항 정리 → 리서치 → 계획서 → [사람 승인] → 구현 → 테스트 → 리뷰 → 회고/인수인계
```

## 단계별
| 단계 | AI에게 요청할 것 | 사람이 확인할 것 | 산출물 |
|---|---|---|---|
| **0. 요구사항 정리** | 요구사항을 한두 문장으로 요약·모호한 점 질문 | 무엇을 왜 만드는지 합의됐나 | 요구 요약 |
| **1. Research** | 관련 코드·데이터 흐름·기존 패턴을 상세히 조사(`/research-plan`) | AI가 시스템을 제대로 이해했나(틀리면 계획도 틀림) | `docs/plans/<날짜>-<기능>.md`의 리서치 절 |
| **2. Plan** | 리서치 기반 단계별 구현 계획서 작성 | 접근이 맞나·범위가 적절한가. **인라인 노트로 수정** | 계획서(승인 대기) |
| **3. Approve** | (대기) | **사람이 명시적으로 승인.** 미승인 계획은 구현 X | 승인된 계획서 |
| **4. Implement** | 승인된 계획만 구현(`/implement-from-plan`). 계획 밖 변경 금지 | 계획 대비 이탈 없나 | 코드 변경 |
| **5. Test** | 테스트 전략 수립·작성·실행(`/test-plan`) | 테스트가 의미 있나(무의미한 통과 아님) | 테스트 + 결과 |
| **6. Review** | 변경 리뷰(`/review-checklist` 체크리스트) | 버그·보안·복잡도·일관성 | 리뷰 결과·수정 |
| **7. Handoff** | 인수인계 문서(`/handoff`) | 다음 세션/사람이 바로 이어받을 수 있나 | `docs/handoff/<날짜>.md` |

## 4단계 Implement — 두 갈래
| 조건 | 방식 |
|---|---|
| 태스크 3개 이하 · 서로 얽힌 변경 | `/implement-from-plan` — 메인 세션이 직접 구현 |
| 태스크 4개 이상 · 대체로 독립 | `/subagent-driven-development` — 태스크별 신규 구현자 + 태스크별 리뷰어 + 최종 whole-branch 리뷰 |

후자는 구현자와 리뷰어를 분리해 **자기 코드 자기 검토**를 구조적으로 차단한다. → `docs/dev-workflow/roles.md`

## 막히면 — 디버깅은 별도 절차
버그·테스트 실패·예상 못한 동작은 이 흐름에서 빠져나와 `/systematic-debugging`으로 간다.
**근본 원인 조사 전 수정 금지**, 3회 실패 시 아키텍처를 의심하고 사람에게 보고.

## 규칙
- **계획 승인 전 구현 금지.** 급하면 계획을 짧게, 그래도 승인은 받는다.
- 리서치가 부실하면 계획·구현이 다 틀린다 → 리서치에 시간을 쓴다("상세히·빠짐없이" 명시).
- 참조 구현이 있으면 그걸 제시한다 — AI는 백지 설계보다 참조가 있을 때 훨씬 잘한다.
- 커밋은 의미 단위, **push/PR은 사람 승인 후.**
